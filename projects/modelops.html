ModelOps

The challenge

Training a model is only one part of an operational ML system. Inputs can drift, performance can change, and retraining can be harmful when model replacements are not evaluated consistently. ModelOps explores what a controlled model lifecycle should look like.

The platform is a synthetic demonstration built to make release decisions observable, reproducible and understandable.

How it works

A baseline churn classifier is trained on synthetic data. Monitoring compares historical and incoming cohorts using PSI and KS statistics. If retraining is needed, a challenger is trained and evaluated alongside the current champion on consistent holdouts. Decision checks control promotion, and the previous champion is archived.

Data → train & version → serve → monitor drift/performance → evaluate challenger → gated promote or reject.

Evaluation & decisions

MLflow tracks experiment configurations, metrics and artifacts. The API uses FastAPI validation; the Streamlit application exposes operational workflows. GitHub Actions and pytest are used for automated checks. Promotion is explicit and separate from merely registering a candidate.

A drift alert alone is not sufficient justification for replacing a model. The project intentionally distinguishes dataset shifts, evaluation results and operational decisions.

Engineering considerations

The demonstration uses synthetic customers rather than real production traffic. Model artifacts and tracking metadata may be local or ephemeral depending on the deployment. A public dashboard and API are documented in the repository, but the actual deployment and public sharing settings should be checked.

The project models governance mechanics; it does not promise a production-grade, always-on ML platform or a zero-delay API.
